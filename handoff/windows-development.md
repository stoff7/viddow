# Передача в разработку Windows-порта

12 ноября 2026. Пользователь попросил подготовить старт следующей сессии.
Это задание на реализацию по уже выполненному аудиту, а не повторный аудит.

## Прочитать в таком порядке

1. HANDOFF.md — состояние/ограничения.
2. windows-audit.md — проверенные места и контракт; база d2fd8c4, аудит 7c8fe20.
3. windows-plan.md — цель установки, системные различия и матрица приёмки.
4. Актуальные install_native_host.py, native_host.py/.sh, download.py,
   native_session.py и вызывающие run_tool модули.

Начальная точка приложения — b2b2abe (v3.4.0). На момент передачи tracked-дерево
чистое, HEAD до handoff 7c8fe20; untracked .agents/, skills-lock.json и
handoff/experiments/ принадлежат пользователю. Не включать их в коммиты порта.
Не начинать заново UI, очередь, media identity, HLS tracks и историю.

## Первый результат: технически рабочий путь, не установщик

Предлагаемый охват Windows x64 + Chrome/Edge. Минимальная Windows, runtime
и машина для исполнения пока не выбраны. В начале определить имеющуюся среду;
если нужна машина пользователя, спросить о ней, продолжая независимые изменения.
Не объявлять Windows 10/11 поддержанными без выбранной базы и проверки.

### A. Native Messaging

- Принимать реальный ID распакованного расширения, проверять формат, формировать
  allowed_origins; не использовать macOS hash пути как доказанный Windows ID.
- Создать Windows entry point с предсказуемым runtime, бинарным stdio и без
  произвольного вывода в stdout. Сохранять аргументы браузера. Не выбирать
  pythonw только ради скрытого окна: проверить наличие и работу stdio.
- Добавить явную ветку Windows установщика с HKCU Chrome/Edge, абсолютными
  путями и идемпотентным install/uninstall. Точные ключи/views/API сверить
  с официальными источниками из аудита перед реализацией.
- Изолировать тестовую регистрацию: отдельный пользователь/VM либо точное
  сохранение/восстановление затронутых ключей. Один --user-data-dir не изолирует HKCU.
- Проверить handshake и несколько сообщений, Unicode, частичное/оборванное
  сообщение, неверный ID/путь, EOF. Использовать настоящую связь браузер→host.

Результат: техническая установка подключает helper в Chrome/Edge без изменения
глобального PATH и обязательного администратора. Скачивание ещё не объявлять готовым.

### B. Владение деревом процессов — до широкого рефакторинга

Сделать маленький Windows-прототип на безвредных дочерних процессах и выбрать
надёжный способ назначения Job Object до выполнения дочернего кода. Учесть
вложенный job браузера, наследование handles, kill-on-close и закрытие ресурса.
Не использовать приватные детали CPython без обоснования выбранного runtime.

Критические сценарии: потомок создан и родитель уже вышел; отмена до/после
запуска; watcher и finally останавливают одновременно; обычный EOF и аварийное
завершение host; потомок удерживает pipe или temp-файл. Готовый файл не удаляется.
Критерий — нет своего живого дерева/утекших handles, pipe закрыт, cleanup завершается.
Terminate родителя и mock вызова stop не заменяют этот результат.

Сначала доказать механизм, затем подключить его в run_tool для download,
inspector, preview и probe. Не создавать отдельную Windows-очередь.
Если stdlib/ctypes становится сложнее обоснованной библиотеки, оформить короткое
ADR с альтернативами; не вводить зависимость молча ради удобства.

## После прототипов: интеграция небольшими изменениями

1. platform_support.py по контракту аудита: resolver, системные пути, reveal,
   владелец процессов; installer и bootstrap остаются отдельно.
2. Один resolver для state и запуска во всех модулях; обеспечить также доступ
   yt-dlp к ffmpeg/ffprobe и Deno/Node. Неверный явный путь не скрывать fallback.
3. Known Folder Downloads только при отсутствии пользовательской папки; Explorer
   по действию пользователя. Сохранить проверки доступа session и legacy reveal.
4. stdin инструментов DEVNULL, согласованная кодировка stdout JSON/stderr,
   приватность prepared info-json с Windows ACL, cleanup после остановки дерева.
5. Windows-имена и длины; гонку finalization/os.replace исправить отдельным
   коммитом с регрессией на конфликт уже появившегося файла. Не перезаписывать его.
6. Пользовательский каталог логов и межпроцессная запись/ротация; понятные
   платформенные подсказки, разбор Windows-путей в UI. Не превращать это в редизайн.

## Доказательство готовности и порядок проверки

Тесты не гонять после каждого изменения. Выполнять согласованные проверки
завершающим этапом законченной части; полный набор автоматически не запускать.
Прежние UI-запреты не являются доказательством совместимости: явно отделять
неисполненные Windows-сценарии. Текущая передача сама тестов не запускает.

Минимальная реальная проверка после интеграции:
- чистая Windows, оба браузера, бинарный native-протокол;
- прямой файл, HLS с настоящими сегментами, отдельные video/audio и ffprobe результата;
- отмена/закрытие браузера без потомков, повтор, история после перезапуска;
- кириллица/пробелы/перенесённая Downloads, занятый файл/нет прав;
- показ файла только по клику, macOS регрессия изменённых общих путей.

Существующие native/browser fixtures ориентированы на macOS и старые UI-селекторы:
адаптировать адресно. os.kill(pid, 0) не переносить как Windows-проверку живости.
Mock-контракты, реальные инструменты и реальный браузер описывать раздельно.
При отсутствии Windows продолжать переносимые части, но фиксировать блокер
именно исполнения, не выдавать статический код за готовый порт.

## Упаковка — последняя стадия

После рабочего технического пути выбрать runtime/упаковщик, комплектные версии
инструментов, installer/update/uninstall, лицензии и отдельный Windows-артефакт.
Проверять распространяемый пакет на чистой машине, не только исходники.
Ничего не публиковать, не менять тег v3.4.0 и main без отдельного указания.
Коммиты должны отделять протокол/регистрацию, процессы, общие исправления и упаковку.
