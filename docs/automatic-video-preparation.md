# Автоматическая подготовка видео и загрузка одной кнопкой

12 ноября 2026. Требование пользователя: Unsupported URL у страницы автоматически
исправляется переходом к найденным видео. Пользователь видит видео, картинку,
качество и «Скачать»; сетевые потоки остаются техническими подробностями.

## Контракт и ограничения

- Используем существующий yt-dlp/ffmpeg, native-сессию и очередь; никаких daemon,
  UI-фреймворков или новых runtime-зависимостей. Web/CLI не меняются.
- После unsupported_source у страницы — одна ограниченная партия до 6 HLS/DASH,
  максимум 2 анализа одновременно, 12 секунд на кандидата. Дедупликация общая
  для панелей. Если потоков ещё нет, ждём их появления. Саму страницу не повторяем.
- Допускаются только запросы актуального документа вкладки из видимой цепочки
  iframe. Несколько media одного документа не считаются одним видео. Явно
  выбранный плеер ограничивает кандидатов своим документом; при нескольких blob
  в нём без точной связи автоматическое скачивание не назначается. Пользователь
  разрешил автоматически рекомендовать лучший пригодный вариант среди кандидатов;
  это рекомендация, не утверждение, что кандидаты содержат одинаковый ролик.
- Кандидаты анализируются по полному URL и с собственными заголовками. Они не
  объединяются по имени, пути, порядку или совпадению картинок. Ошибка одного не
  скрывает пригодный другой. Явный выбор сильнее рекомендации.
- По умолчанию предпочитаем подтверждённое видео со звуком/возможностью объединения,
  затем известное разрешение и битрейт. Неизвестные параметры ниже подтверждённых.
  fps вне (0, 240] скрывается как недостоверный, без угадывания 22500 → 22.5.
- Источник и ID формата выбираются вместе; native повторно проверяет оба. Кнопка
  не отправляет исходную неподдерживаемую страницу после успешного fallback.
- Подготовка сама не скачивает полный ролик. Явное нажатие «Скачать» во время
  подготовки разрешает один запуск после её успешного окончания. Отмена, смена
  документа/вкладки, ручной выбор другого источника или смена native-сессии снимают
  отложенный запуск. При неоднозначном звуке требуется выбрать дорожку.
- GIF необязательна для загрузки: ffmpeg читает начало подтверждённого video URL,
  до 2 секунд/8 кадров, 320×180, до 128 КиБ, таймаут 8 секунд, максимум 2 превью
  одновременно. Результат передаётся отдельным reply, не полным native state.
  Без кадра используются thumbnail/poster того же источника или подписанная заглушка.
  Canvas/DOM не воспроизводится и не перематывается. Нет общего pageImage fallback.
- Временные файлы удаляются; картинки/секреты не пишутся в историю/диагностику.
  Не читаем личные cookies, не открываем Finder. Внешние сайты проверяем отдельно
  от локальной реальной HLS-фикстуры. DRM не обходится.

## Приёмка

Неподдерживаемая локальная HTML-страница с несколькими настоящими HLS: один
непригодный/неизвестный, другой с известным разрешением и звуком. Автоматическая
подготовка, рекомендация второго, GIF, выбор альтернативы и реальный файл через
кнопку «Скачать». Не более одной партии из двух панелей. Отмена/навигация/поздние
ответы не запускают загрузку. Заголовки и query сохраняются. Пустой/CORS/ошибка
превью не ломают скачивание. Отдельно проверяем недостоверный fps и чужие format IDs.

## Протокол и проверенные результаты

`inspect` принимает необязательные `fallbacks` (до 6 обычных проверенных запросов
HLS/DASH) и `fallback_only`. Снимок analysis содержит page и result.videos;
каждое видео имеет непрозрачный id, source_url, собственные formats и
recommended_format_ids. Полные URL **форматов** и их заголовки остаются внутри
Inspector. `download` с analysis_id принимает необязательный source_id и
проверяет ID формата в выбранном источнике. Обычный одиночный анализ и прежний
native v2 download сохраняются. Источник и заголовки копируются до анализа.
Общий JSON результата ограничен 512 КиБ; самые низкие рекомендации отсекаются
при превышении, а не ломают native-канал.

`preview` принимает analysis_id/source_id и асинхронно отвечает отдельным reply
с ограниченным GIF data URL. Main loop продолжает обрабатывать очередь и отмену.
Превью одного источника создаётся один раз на анализ; две панели используют общую
запросную дедупликацию. Новый анализ/сеанс отменяет старые операции. Source URL
содержит query только в текущей сессии; GIF не входит в history/native state.
Для прямого подтверждённого DOM-соответствия можно сохранить кадр/poster при
отсутствии thumbnail; по одному frame или совпадению картинки источники не склеиваются.

Подтверждено локально:

- 27 JS-тестов и 14 Inspector-тестов, 5 тестов native-протокола.
- `tests/extension_smoke.cjs`: прежние UI/очередь/история/две панели/диагностика.
- `tests/automatic_video_native_smoke.cjs`: настоящий SIDE_PANEL → native host →
  yt-dlp → HLS с действительными сегментами → MP4. Страница не поддерживается
  generic extractor; из двух кандидатов рекомендован 720p со звуком, а неизвестный
  вариант доступен в списке. Обе загрузки проверены; рекомендованная — ffprobe
  (720p + аудио). Query и отдельные X-Video заголовки дошли до запросов сегментов.
  После раннего нажатия «Скачать» до появления потоков выполнена одна загрузка,
  без второго клика. Открытие второй панели не заменило анализ.
- Настоящий GIF: 320×180, 8 кадров, не более 128 КиБ; файл проверен ffprobe.
  Изображение не попало в storage.local/history/nativeState. Снимок интерфейса
  `/tmp/viddow-auto-native/recommended-400.png`, GIF `/tmp/viddow-auto-native/preview.gif`.

В старом native-тесте изолирована заглушка Finder: patch общего subprocess.run
ошибочно перехватывал и системные вызовы записи macOS метаданных. Исправление
касается только теста, Finder в проверках не открывался.

Реальный reinkarnatciya-bezrabotnogo-animego.ru не подтверждён: попытка чтения
страницы через web завершилась timeout. Личные cookies не использовались.
Проверка локальной неподдерживаемой страницы доказывает общий fallback-путь,
а не доступность конкретного CDN/серии. X и произвольная связь blob с manifest
по-прежнему не объявляются поддержанными. Это рекомендация из актуальных
видимых запросов, а не распознавание тождества роликов по GIF.

Для применения файлов расширение нужно однократно перезагрузить: это также
перезапустит Python native host. Дальнейшая ошибка Unsupported URL обрабатывается
автоматически при наличии подходящих наблюдаемых запросов. Если расширение ещё
не наблюдало запросов этого видео, они появятся при его обычном запуске в плеере.

Механика ограничения ffmpeg описана в [официальной документации](https://ffmpeg.org/ffmpeg.html).
Основной загрузчик сохраняет [параллельную загрузку фрагментов yt-dlp](https://github.com/yt-dlp/yt-dlp#download-options).

## Исправление ожидания перед анализом

Сообщение «Идёт подготовка. Дождитесь результата или отмените её» может означать
ожидание ответа background до старта native-анализа. Опрос scripting прежде
ожидал Promise всех iframe без общего дедлайна; таймеры внутри скрытых документов
могут задерживаться браузером. Контракт исправления: скрытые iframe не опрашиваются;
связи конкретных iframe с токенами документа кешируются в isolated world и
проверяются по свежим документам/видимости. Фоновый опрос запускает handshake,
но ждёт только ограниченное окно в worker, затем читает синхронные снимки.
Весь pageContext ограничен 3 секундами, в том числе executeScript, который
вообще не ответил. Неустановленная связь исключается, видимость не угадывается.
При недоступном DOM продолжается ограниченный обычный анализ страницы;
отсутствие DOM-контекста не блокирует ответ панели навсегда.

В диагностике добавлены page_context_start/ready/unavailable с elapsed_ms, без
URL и токенов документов. На первоначальном ожидании панель пишет
«Проверяем страницу и плееры…», отличая его от уже запущенного анализа.

Проверено после исправления: 18 точечных JS-тестов (включая навсегда зависший
executeScript и неотвечающий probe), media_identity_smoke с вложенными/скрытыми
плеерами и лентой из 30 видео. Настоящий automatic_video_native_smoke расширен:
первый фоновый executeScript намеренно не отвечает; спустя 3 секунды запускается
обычный native-анализ, заканчивается, кнопки освобождаются и в журнале есть
page_context_unavailable. Реальный fallback/GIF/скачивание также прошёл.

## Наблюдаемый поток без DOM-привязки и сквозной журнал

Уточнение пользователя: поток уже виден в технических подробностях, а подготовка
пишет «Ждём появления видео». Причина в смешении двух проверок: пригодность
сетевого источника и доказанное соответствие DOM-плееру. Источник текущего
поколения вкладки можно ограниченно анализировать и получить его собственную GIF,
даже если scripting не видит documentId или iframe не ответил. Это не разрешает
приписывать ему poster/duration другого DOM-video. Подтверждённо скрытые документы
и источники прежнего поколения исключаются; явный выбор плеера сохраняет приоритет.
Если адрес есть, но он исключён, интерфейс показывает причину, а не отсутствие видео.

Добавляется файл `logs/viddow.jsonl`, доступный для чтения из репозитория:
сквозные события расширения, отбора кандидатов, native-анализа, превью и очереди.
Ротация: 512 КиБ + одна резервная копия. Только коды событий, счётчики, время,
непрозрачные ID и числовые frame/tab ID. Полные URL, заголовки, cookies, пути
скачивания, названия и сырые ошибки не записываются. Журнал не коммитится.
Тесты используют отдельный `VIDDOW_TRACE_FILE` в /tmp. По просьбе пользователя
все проверки запускаются одним завершающим этапом после реализации, не по ходу правок.

Для сетевого источника без documentId учитывается поколение вкладки из webRequest,
а не домен CDN/путь URL. Тип HLS/DASH из Content-Type сохраняется, поэтому адрес
в корне CDN `/` с query также проверяется. При наличии адресов, которые исключены,
новая фаза blocked объясняет причину вместо ложного «Ждём появления видео».

Поколение вкладки восстанавливается из согласованного session-кеша при пробуждении
MV3 worker. Иначе уже обнаруженный адрес снова терял область актуальности после
обычного простоя расширения. Смешанные поколения не восстанавливаются; событие
новой навигации/запроса сильнее результата асинхронного чтения кеша.

Завершающие проверки этой правки: 34 JS-теста, 26 Python-тестов журнала/Inspector/
очереди/native-протокола. Реальный native smoke воспроизводит один HLS-адрес в
корне CDN без documentId и подтверждает готовый файл. В его файловом журнале
прочитана цепочка stream_seen → prepare_candidate(current_generation) →
candidate_done → analysis_done → preview_done → download_queued → job_done;
сырых URL/заголовков в файле нет. Также прошли media_identity_smoke и mock UI smoke.
Журнал этого прогона: /tmp/viddow-auto-native/trace.jsonl; рабочий журнал проекта
создан пустым и начнёт пополняться после запуска обновлённого native-host.

В UI smoke исправлено ожидание нового native-запроса: используем явный ограниченный
опрос worker, потому что async-предикат waitForFunction в установленной сборке
Playwright воспринимается как truthy Promise до завершения проверки. Это касается
тестового ожидания, не поведения приложения.
