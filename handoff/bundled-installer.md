# Viddow со всем необходимым внутри: план реализации

14 ноября 2026. Пользователь хочет избежать отдельной установки yt-dlp/ffmpeg.
Согласованное направление — локальный помощник с комплектными инструментами.
Код упаковки ещё не создан, конкретные версии/упаковщик/installer не выбраны.

## Пользовательский результат

Установить расширение → скачать и установить Viddow → скачивать из панели.
Не нужны установленный Python, терминал, brew/pip, ручной PATH и регистрация host.
Расширение остаётся отдельным компонентом: отсутствие helper показывает понятное
действие «Установить Viddow», после установки — «Проверить подключение».
Не подменять отсутствие helper сообщением «установите ffmpeg».

Первый пакет полный: runtime и инструменты уже внутри. Интернет необходим для
видео, но не для докачки зависимостей при первом старте. Это увеличит размер,
зато уберёт ошибки bootstrap-загрузки. Маленький сетевой installer отложить.

## Состав и открытые решения

- Исполняемый native-host с комплектным Python-runtime или упакованным Python-кодом.
  Сравнить на коротком прототипе folder-based bundle и автономный executable;
  не выбирать single-file только из-за внешнего удобства. Учесть распаковку,
  время старта, temp, дочерние процессы и подпись.
- yt-dlp, ffmpeg, ffprobe; необходимые для обещанных источников impersonation,
  JS-runtime/EJS и прочие компоненты выбрать по конкретному релизу yt-dlp.
  Наличие бинарника не доказывает поддержку этих возможностей.
- Native manifest/registration, версия сборки, component manifest и notices.
- Отдельные артефакты macOS/Windows и архитектур. Начать с доступной macOS;
  Apple Silicon/Intel или universal — явное решение по возможностям компонентов.
  Windows первая цель 11 x64; готовность этой платформы пока не доказана.

До решения проверить официальные инструкции выбранного упаковщика, yt-dlp,
Chrome/Edge и ОС. Настоящий документ не фиксирует устаревающие параметры сборки.
Не добавлять второй загрузчик, UI-framework, сервис или новую очередь.

## Этап 1. Контракт пакета и технический прототип

Прочитать platform_support.py, native_host.py/native_protocol.py, native_host.sh,
install_native_host.py/windows_native_install.py, исходные Windows ADR.
Разделить immutable файлы приложения и writable данные/логи/parts/settings.
Каталог исходников и cwd не должны быть необходимы установленному приложению.

Описать install root, пути runtime/bin, локатор ресурсов, пользовательский data/log
каталог и поведение explicit tool overrides. В пользовательском bundled-режиме
не подхватывать случайный глобальный yt-dlp/ffmpeg: отсутствие комплектного файла
должно быть видимой ошибкой пакета. Dev-режим с текущими overrides сохранить.
Реальный запуск и state.tools используют один resolver.

Стабильный ID расширения/allowed_origins обязателен: dev-режим может принимать
фактический ID, публичный пакет требует определённого канала распространения.
Не расширять allowed_origins произвольно и не полагаться на hash пути macOS.

Первый артефакт — локальный комплектный host, который запускается браузером,
обменивается ready/state/reply и скачивает валидный HLS video+audio без системных
инструментов. Упакованный host сохраняет бинарный stdin/stdout, EOF/cancel,
диагностику вне stdout. pythonw/GUI executable не считать решением без проверки.

## Этап 2. Воспроизводимая сборка

Добавить build-скрипты и manifest компонентов: фиксированные версии, архитектуры,
источники скачивания, хеши, лицензии и совместимость. Бинарные файлы не класть
случайно в git; выпускать артефакты. Не скачивать latest без фиксации при сборке.
Не встраивать локальные пути/секреты/пользовательский профиль разработчика.

Проверить выбранные лицензии/условия распространения конкретной сборки ffmpeg
и остальных компонентов по первичным источникам; комплектовать notices и нужные
материалы. Не считать все ffmpeg-сборки юридически и функционально одинаковыми.
Подписывать/notarize macOS и подписывать Windows-пакет при публичном выпуске,
согласно доступным credentials. При отсутствии сертификатов обозначить это
как границу test build; не отключать защиту ОС и не обходить quarantine.

## Этап 3. Установка, восстановление и удаление

Первый формат installer выбрать после прототипа. Автоматически установить файлы
в постоянное место и зарегистрировать manifest в поддерживаемых браузерах.
По возможности user-level, без глобального PATH и ненужного администратора.
Повторная установка и repair идемпотентны; чужую регистрацию не перезаписывать.
Поддержка браузера подтверждается реальным подключением, не наличием каталога.

UI без helper предлагает платформенный пакет и ручную проверку подключения.
Не вызывать загрузку/установку executable автоматически из страницы. Подготовить
реальные ссылки на релиз только после его публикации; не оставлять фиктивные.
При изменении extension UI применить локальные chrome-extensions/modern-web-guidance.

Uninstall удаляет только приложение и его регистрацию. Видео, история расширения
и незавершённые пользовательские загрузки не удаляются молча. Перемещение пакета,
старый manifest, несколько установок и отсутствие разрешений дают понятный исход.

## Этап 4. Обновление

Первый выпуск обновляется полным проверенным пакетом. Версионированные каталоги,
проверка перед переключением, сохранение рабочей версии для отката. Не заменять
бинарники активных задач; обновление дождётся их завершения/явного решения пользователя.
История/настройки и native-протокол совместимы, несовместимость объясняется в UI.

Независимые обновления yt-dlp полезны, но отдельная стадия: проверенный канал,
подпись/доверенный manifest, хеш, совместимость с runtime и компонентами, откат.
Не вызывать self-update произвольно внутри подписанного app bundle и не скачивать
непроверенный исполняемый файл при каждом старте. SHA-256 без доверенного источника
сам по себе не доказывает происхождение файла.

## Этап 5. Приёмка именно пакета

Проверки завершающим этапом, не после каждой правки. Минимальная чистая среда
не содержит Python, Homebrew, yt-dlp, ffmpeg или подходящего PATH разработчика.
Пустого PATH на dev-машине недостаточно как единственного доказательства.

- Chrome/Edge Windows и заявленные macOS-браузеры: install → connect → реальное
  скачивание → cancel → повтор → restart/history → показать файл по клику.
- Прямой файл, HLS, раздельные video/audio: ffprobe подтверждает состав и длительность.
- GIF, нужные yt-dlp capabilities, кириллица/пробелы, нестандартная папка установки.
- Binary stdio, отсутствие лишних окон, EOF и остановка всех дочерних процессов.
- Нет доступа к install root для записи: логи/parts не ломают загрузки.
- Повтор install/repair, обновление при активной задаче, сбой обновления/rollback,
  uninstall без потери файлов, отсутствующий/повреждённый компонент.
- Проверить архитектуры отдельно; хранить результаты/версии и ограничения в отчёте.

Windows-блокеры прежние: Job Object не production, Known Folder/Explorer/ACL и
настоящий Chrome/Edge→host не приняты. Упаковка их не устраняет. Работу macOS
можно продолжать независимо, Windows-пакет не объявлять готовым по mock на macOS.

## Порядок работы и границы текущего задания

Сейчас пользователь запросил handoff, не установку на его машину и не публикацию.
Следующая сессия: ADR/раскладка → macOS комплектный прототип → воспроизводимая
сборка → installer/repair → приёмка → подготовка выпуска. Windows отдельной ветвью
этого же плана после закрытия runtime-блокеров. Коммиты небольшие по этапам.
Не менять v3.4.0, main и удалённый release без явной просьбы. Пользовательские
.agents/, skills-lock.json и экспериментальные patch не включать автоматически.

Первое практическое задание: собрать локальный helper с инструментами для macOS
и доказать реальную загрузку без системного Python/yt-dlp/ffmpeg; до сборки выбрать
и документировать runtime, расположение ресурсов и источник каждого компонента.
