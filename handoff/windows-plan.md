# План поддержки Windows и переносимости Viddow

12 ноября 2026. Пользователь попросил записать предложение полностью с пояснениями.
Это план, не реализованная/проверенная поддержка Windows. База — релиз v3.4.0.

Статус: этап 1 выполнен как статический [аудит платформенных зависимостей](windows-audit.md)
на базе `d2fd8c4`; там сохранены места в коде, приоритеты, контракт адаптера,
официальные источники и проверки следующего этапа. Реализация первого технического
этапа начата: [актуальный статус](../docs/windows-development.md); Windows-исполнение
и интеграция загрузчика ещё не подтверждены.

## Цель и первая область поддержки

Одно расширение и общая логика загрузчика для macOS/Windows. Различаются установка
native-host, поиск инструментов, системные папки, показ файла и управление процессами.
Предлагаемый первый охват: Windows x64, Chrome и Edge. Конкретную версию Windows,
архитектуру и доступную тестовую машину определить в начале; ARM64/Linux/остальные
Chromium-браузеры не обещать до проверки. Решения по упаковщику пока не приняты.

Пользовательский путь: установить расширение → запустить установщик Viddow →
открыть панель и скачать. Не требовать ручного PATH, Python и Homebrew-команд.
Техническую установку для разработки можно сделать раньше удобного установщика.

## 1. Аудит и минимальная граница платформы

Прочитать install_native_host.py, native_host.sh, native_host.py, native_session.py,
download.py, media_prepare.py, media_tracks.py, inspector.py, macos_metadata.py,
source_auth.py, диагностику и build/release-скрипты. Найти POSIX signals/chmod,
временные файлы, пути, shell, open, предположения о PATH и кодировке.

Вынести небольшой модуль (имя выбрать по структуре проекта), например функции:
- default_download_dir(): системная папка загрузок;
- resolve_tool(name): комплектный инструмент или явно заданная/системная установка;
- reveal_file(path): показать готовый файл в менеджере файлов;
- запуск и завершение только дерева процессов конкретной задачи.

Регистрация/упаковка остаются отдельно от логики загрузки. Не делать большой
абстрактный framework, не переписывать очередь, историю, UI и протокол ради ОС.
Обновить диагностические инструкции: macOS brew не показывать как решение Windows.

## 2. Native Messaging на Windows

Сделать Windows launcher/host и регистрацию в пользовательской области реестра
для целевых браузеров, без обязательного запуска администратором. Перед реализацией
проверить официальные контракты Chrome/Edge: точные ключи, разрядность registry view,
правила path/allowed_origins и формат запуска. Не копировать macOS схему папок.

Критически важно:
- stdio — двоичный канал длина+JSON, без CRLF-преобразований и консольных логов
  в stdout. Проверить в упакованной версии, а не только Python из терминала;
- стабильный ID расширения и allowed_origins. Текущий вычисленный из macOS пути
  ID нельзя считать подходящим для распакованного расширения на Windows;
  определить способ передачи реального ID/стабильной публичной identity;
- отсутствие консольных окон не должно ломать stdin/stdout native-протокола;
- повторная установка идемпотентна, удаление снимает только регистрацию Viddow;
- закрытие браузера/EOF останавливает принадлежащие хосту задания.

Приёмка: чистый профиль Chrome и Edge подключает helper, ready/state/reply работают;
нет helper/неправильный ID/неправильный путь дают понятную диагностику.

## 3. Инструменты и упаковка

Сначала подтвердить рабочую установку с явными путями к Python, yt-dlp, ffmpeg,
ffprobe. Затем выбрать комплектный runtime или упаковку Python-host в executable.
Проверить поддержку требуемого impersonation yt-dlp и JS-runtime для источников,
не считать любой yt-dlp.exe эквивалентным текущей macOS сборке.

Рекомендуется отдельный Windows-пакет с зафиксированными версиями инструментов
и предсказуемым поиском рядом с приложением. Не менять глобальный PATH и не зависеть
от случайного executable из текущего каталога. Учесть обновление yt-dlp, размер,
лицензии распространяемых бинарников и происхождение сборок. Новые зависимости
выбирать только при реальной необходимости; конкретный installer пока не выбран.

Установщик в пользовательскую папку, manifest и регистрация с абсолютным путём.
Обновление не прерывает активную задачу молча; файлы занятого процесса учитываются.
Удаление программы по умолчанию не удаляет скачанные видео и браузерную историю.
Подпись Windows-пакета и доверие при запуске оценить для публичного распространения;
не предлагать пользователю отключать защиту ОС. ZIP + SHA-256 не заменяют подпись.

## 4. Системная папка, имена и показ файла

Получать Downloads через системный механизм Windows Known Folders, проверить
перенесённую папку/OneDrive. Пользовательский выбор папки имеет приоритет.
Не строить путь из предположения C:\Users\имя\Downloads.

Проверить зарезервированные имена Windows, запрещённые символы, конечные точки/
пробелы, коллизии без учёта регистра, длинные пути, кириллицу, emoji, пробелы.
Не изменять существующие пользовательские файлы при исправлении имени.
Ошибки прав/занятого файла/отключённого диска/полного диска должны быть понятными.

Показать готовый файл через Explorer с выделением. Использовать аргументы/API
без склейки shell-команды. Путь берётся из результата задания, а не произвольного
сообщения панели; проверить существование. Действие выполняется только по клику.
macOS metadata остаётся платформенной best-effort-функцией, не вызывается Windows.

## 5. Отмена, временные файлы и завершение

POSIX killpg не переносится на Windows напрямую. Спроектировать надёжное владение
деревом yt-dlp/ffmpeg/ffprobe (например, оценить Windows Job Objects), включая
гонку рождения потомка, ранний выход родителя, quiet subprocess и EOF браузера.
Не использовать широкое завершение по имени процесса: другие загрузчики пользователя
не принадлежат Viddow. При отмене освобождаются файлы и место очереди после остановки.

Windows блокирует открытые файлы иначе: проверить cleanup/rename временных файлов,
антивирусные задержки, read-only/занятые пути, сохранение готового файла при поздней
отмене. 0600 у prepared info-json не считать доказательством приватности Windows:
проверить каталог/ACL и удаление чувствительного контекста после выполнения.

## 6. Проверки и критерии выпуска

| Сценарий | Ожидаемый результат |
| --- | --- |
| Чистая Windows без dev-инструментов | Установка и подключение без ручного PATH |
| Chrome и Edge | Панель, обнаружение, очередь и native-сеанс работают |
| MP4 / страница / HLS | Сохраняется правильный выбранный ролик |
| Раздельные video/audio | ffprobe подтверждает обе дорожки в результате |
| Отмена, закрытие браузера | Нет оставшихся дочерних процессов/заблокированных частей |
| Повтор и перезапуск | История сохранена, прерванные не стартуют сами |
| Показать файл | Explorer выделяет существующий результат по клику |
| Кириллица, пробелы, перенос Downloads | Файл сохраняется в правильное место |
| Занятый файл, нет прав/места | Понятная ошибка, готовые файлы не повреждены |
| Обновление/удаление | Регистрация корректна, скачанные видео сохраняются |
| macOS регрессия | Существующая установка/отмена/reveal работают |

Локальные unit/mocks полезны для контрактов, Windows CI — для платформенных частей,
но реальные Chrome/Edge+host нужны отдельно. Проверять пакет, который будет
распространяться, не только исходники на машине разработчика. Нет Windows-среды —
честно зафиксировать внешний блокер проверки и не объявлять совместимость готовой.
Прежний запрет тестов на UI не считать результатом приёмки Windows; согласовать
доступный режим проверки, выполнять разрешённые проверки завершающим этапом.

## Последовательность коммитов/артефактов

1. Аудит и платформенный контракт с найденными местами и решениями.
2. Минимальный адаптер + рабочий Windows host/регистрация для разработки.
3. Отмена/пути/reveal и точечные Windows-проверки, macOS регрессии.
4. Упаковка инструментов, installer/update/uninstall, воспроизводимая сборка.
5. Документация и отдельный Windows ZIP/installer + SHA-256 с честной матрицей ОС.

Версию будущего выпуска не назначать заранее. v3.4.0 не переименовывать в
кроссплатформенный релиз без проверенного артефакта. Публикация/merge — по явной
просьбе. Реализация первого технического этапа начата, остальные этапы ожидают
подтверждения прототипов на Windows.
