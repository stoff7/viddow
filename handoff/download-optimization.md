# Оптимизация загрузок: план следующей сессии

13 ноября 2026. Цель — уменьшить время до правильного готового файла и потерю
работы при обрыве, сохранив отзывчивость браузера. Максимальная мгновенная скорость
сама по себе не критерий. Реализация оптимизаций ещё не начата.

## 0. Сохранить базу

Сначала изучить незакоммиченные общие изменения Windows-порта; не заменять resolver,
кодировки, DEVNULL и finalize_file прежними реализациями. После проверки diff
сохранить законченную общую часть отдельно от оптимизаций; эксперимент Job Object
оставить ясно обозначенным прототипом. Не включать пользовательские skills/patch.
Не менять main/тег v3.4.0 и не публиковать без просьбы.

## 1. Измерения прежде настройки

Добавить в существующий allowlist диагностики монотонные длительности:
очередь, подготовка/анализ, первые реальные байты, передача, mux/финализация,
общее время; отдельно retries, переданные/повторные байты, если измеримы достоверно.
Не выводить retry count или реальные соединения из предположений; при отсутствии
сигнала оставить неизвестным. Непрозрачный task/attempt ID связывает стадии.
Не писать URL/query/cookies/headers/имена файлов или сырые ошибки.

CPU/память и диск сначала измерять в тестовом harness, не добавлять постоянный
ресурсоёмкий мониторинг пользователю. Не путать процесс yt-dlp с целым деревом.

Локальные сценарии с валидными сегментами: нормальная сеть, задержка ответа,
ограничение пропускной способности, временный 429/5xx, обрыв сегмента; один и два
ролика; GIF включён/выключен; cold/warm анализ. Сохранить параметры инструмента,
число повторов измерения и результаты. Прямой MP4 оценивать отдельно от HLS/DASH.
Запускать проверки только в конце законченного этапа, не после каждой правки.

## 2. Ограничить суммарный параллелизм

Сейчас CONCURRENT_FRAGMENTS=16 на задачу, workers=2 по умолчанию. Сравнить 2/4/8/16,
не объявлять заранее 4/8 лучшими. Флаг yt-dlp применяется не ко всем протоколам.
Сначала простой фиксированный бюджет native-сеанса и распределение при запуске
задачи; динамическую адаптацию вводить только при доказанной пользе.

Описать отдельно лимиты активных загрузок, fragment workers и фоновой подготовки.
Не называть лимит фрагментов точным лимитом TCP: redirects, manifests, retries,
раздельные дорожки и preview добавляют запросы. Справедливость между задачами,
очередь и освобождение бюджета при ошибке/отмене обязательны. Web и другой host
имеют свои менеджеры; не обещать общекомпьютерный лимит без архитектурного решения.
Для источника/CDN рассмотреть отдельный cap, не склеивать произвольные домены.

Приёмка: измеримое время/ошибки не ухудшены выбранной политикой в согласованной
матрице; отмена возвращает ресурсы; нет голодания второй задачи и взрыва запросов.
Менять параметры работающего yt-dlp через перезапуск ради лимита нельзя.

## 3. Приоритет явного скачивания

Нажатое пользователем скачивание и необходимый ему анализ важнее GIF остальных
кандидатов. Сохранить существующие пределы партий и исключение дублей между панелями.
Ограничивать/откладывать необязательную работу, не запускать анализ/GIF на каждый render.
Ошибка картинки не блокирует пригодное видео, явная отмена останавливает ожидание.

Кешировать свежие результаты по подтверждённому media/document generation,
набору форматов и контексту авторизации. Инвалидация при смене серии, вкладки,
native-сеанса/браузерного сеанса и доступности источника. TTL не доказательство
валидности подписанного URL; не использовать старый кеш после отказа бесконечно.
Не сохранять чувствительные format URLs/headers в постоянную историю.

Приёмка: время до первых байтов с открытой лентой/превью сравнимо с baseline;
картинки не дёргаются, выбранное видео не подменяется, background не голодает.

## 4. Ограниченные повторы внутри одной задачи

Первыми рассмотреть временные сетевые сбои и фрагменты. Использовать существующие
механизмы yt-dlp, не писать второй загрузчик. Определить конечный бюджет времени
и попыток, возрастающие задержки; учитывать Retry-After, если он доступен.
Не перемножить внешние повторы с внутренними до непредсказуемой длительности.
401/403, DRM, нет места/прав, неверные форматы не лечить одинаковым retry.
Фрагменты не пропускать ради ложного успеха. Cancel прерывает также ожидание retry.

Временный каталог должен жить всю попытку восстановления. Сам факт существования
.part не гарантирует, что инструмент продолжит его; проверить байты/запросы.
Ошибка смены VPN/IP может требовать новых ссылок; это не повод отключать TLS.

## 5. Resume между задачами/перезапусками — отдельный контракт

Только после внутритаскового восстановления. Управляемый каталог частей с квотой,
сроком жизни, учётом активных владельцев и действием удалить незавершённое.
Различать «приостановить», «отменить» и «повторить»: сейчас отмена очищает части,
не менять её смысл молча. После перезапуска автоматической загрузки по-прежнему нет.

Для прямого HTTP продолжать только при подтверждении версии объекта и корректного
Range-ответа; изменённый объект, 200 вместо 206, некорректный диапазон не дописывать.
Для HLS/DASH доказать тот же контент, формат/дорожки, сегментную последовательность
и init data. Live, истёкшие URL и обновлённые manifest требуют отдельной политики.
Не сравнивать только название/длительность. При сомнении начать новый отдельный файл.

Сохраняемые части отделить от prepared info-json/секретного контекста. История
остаётся безопасной проекцией, не хранилищем cookies и подписанных ссылок.
На Windows учитывать ACL, открытые handles и незавершённую интеграцию Job Object.

Приёмка: обрыв на середине действительно уменьшает повторную передачу;
изменённое видео не смешивается; restart не начинает скачивание сам; квота/cleanup
не удаляют активное или готовое; готовый файл сохраняется при поздней отмене.

## 6. Диск и завершение

Измерить системный temp против рабочей папки на диске назначения, включая внешний
диск. Расположение на одном диске может избежать полного копирования, но это
не универсально быстрее. Не засорять папку результата неуправляемыми частями.
Проверить свободное место с учётом video/audio, mux и возможной копии; оценка
заранее не гарантирует отсутствие ENOSPC. Сохранить финализацию без перезаписи.
Не увеличивать CHUNK_SIZE и не добавлять многопоточный HTTP без измеренного узкого места.

## Первый разумный объём реализации

Начать только с измерений и конфигурируемого ограниченного параллелизма.
Представить результаты сравнения и выбранный default, затем приоритет preview.
Resume не включать незаметно в тот же большой diff. Новые численные defaults,
кеш и каталог частей оформлять проверяемыми контрактами/небольшими коммитами.

Источник доступных механизмов: [официальный yt-dlp](https://github.com/yt-dlp/yt-dlp#readme).
В предыдущей сессии сверялись concurrent-fragments, retry-sleep и continue/part;
перед реализацией сверить конкретную установленную версию и её поведение.
Никакие ускорения или восстановление пока не измерены и не реализованы.
