# Отчёт: измерения, параллелизм и восстановление загрузок

13 ноября 2026. Ветка `feat/download-workspace`. Входные документы:
[HANDOFF](../handoff/HANDOFF.md) и [план](../handoff/download-optimization.md).
Пользователь расширил исходный первый этап до всего handoff и попросил выполнять
тесты после реализации. После этого указания тесты запускались завершающим этапом.

## Результат и границы выполнения

Добавлены измерения стадий, фиксированный бюджет fragment workers, приоритет
скачивания над новой фоновой работой, ограниченные повторы и проверяемое
восстановление прямого HTTP между задачами/процессами. Windows-порт сохранён
отдельно. Универсальное ускорение загрузок не установлено.

Полный запрос имеет оставшиеся части: HLS/DASH между запусками, Windows
persistence и приёмка на внешнем диске не реализованы/не подтверждены. Их нельзя
считать завершёнными по результатам этой сессии. В коде эти границы явные:
сомнительные stream-части не используются, а Windows не сохраняет parts между
исполнениями до проверки ACL и владения процессами.

| Раздел исходного плана | Сделано | Оставшаяся граница |
| --- | --- | --- |
| 0. Сохранить базу | Точные исходные 30 файлов сохранены отдельным коммитом | Windows acceptance по-прежнему нужна |
| 1. Измерения | Monotonic стадии, IDs, локальная матрица, CPU/RSS/disk harness | Реальные CDN и долгие/большие файлы не измерены |
| 2. Параллелизм | Конфигурируемый бюджет host и фиксированные доли, очередь/отмена | Нет общего лимита нескольких host или CDN-группировки |
| 3. Приоритет | Один background slot, конечная отсрочка, отмена, FIFO, инвалидация отказавшего source | Нет прерывания уже начатого GIF; новый дисковый кеш не введён |
| 4. Повторы внутри задачи | Direct: конечные попытки/Retry-After; streams: существующий yt-dlp с backoff и watchdog | Внутренние retries/повторные байты yt-dlp остаются неизвестными |
| 5. Resume между запусками | Direct HTTP/POSIX с strong validator, checksum, Range и блокировкой | HLS/DASH и Windows persistence не реализованы |
| 6. Диск | Direct parts на диске результата, место, квота/TTL/cleanup, управляемый destination temp для yt-dlp | Внешний диск, ENOSPC во время mux и Windows ACL требуют отдельной проверки |

Полный контракт: [download-optimization-contract.md](download-optimization-contract.md).

Main, тег v3.4.0 и удалённые refs не менялись; push/merge/release/install не было.
Рабочие пользовательские загрузки и браузерные профили не использовались.

## Измерения и выбор default

Инструменты: yt-dlp **2026.10.21**, ffmpeg/ffprobe **8.0.1**, macOS.
Сценарий: 12 секунд валидного video+audio HLS, сегменты примерно по 1 секунде;
задержка ответа 80 мс; общий bandwidth cap 512 КиБ/с; первый запрос каждого
сегмента получает 429/503 либо обрывается. Две задачи используют один fixture
source, поэтому счётчик первого отказа общий, как и серверный bandwidth cap.
Данные не моделируют произвольный CDN. Ошибки, запросы и отправленные байты
считает локальный сервер; peak_requests не называется числом TCP connections.

Первичная матрица: 96 HLS-прогонов (6 сценариев × 2 числа задач × 4 настройки ×
2 повтора) и 4 отдельных direct MP4. Порядок перемешан с seed=13.
Все 100 прогонов успешны; ffprobe подтвердил video+audio и полную длительность.

Медиана времени до готового HLS, **мс**, первичная матрица:

| --- | ---: | ---: | ---: | ---: | ---: |
| Обычная | 1 | 872 | 830 | 890 | 867 |
| Обычная | 2 | 932 | 1018 | 984 | 972 |

| Задержка | 2 | 2674 | 2092 | 1857 | 1730 |

Меньшие значения не дали общей пользы и заметно замедлили ошибки/latency.
Поэтому выбран **budget=32** и максимум **16 на задачу**. При 1–2 задачах это
сохраняет прежнюю настройку; при workers=8 каждая получает 4 вместо прежних 16,
суммарный бюджет не превышает 32. Последний пример следует из контракта и тестов,
а не из benchmark восьми роликов. Более низкий бюджет остаётся настройкой.
Бюджет ограничивает сумму переданных значений `--concurrent-fragments`, а не
доказывает предел всех внутренних потоков yt-dlp: live DASH generator может
округлять доли между дорожками вверх. Этот режим требует отдельной приёмки.

Итоговая реализация отдельно проверена ещё в 28 прогонах: N=16, 1/2 задачи,
все 6 сценариев по 2 повтора плюс 4 MP4. Все корректны. Медианы:

| Сценарий | 1 задача, мс | 2 задачи, мс |
| --- | ---: | ---: |
| Обычная HLS | 909 | 1052 |
| Задержка HLS | 1630 | 1715 |
| Bandwidth HLS | 3612 | 5914 |
| 429 HLS | 2884 | 3173 |
| 503 HLS | 3262 | 2979 |
| Обрыв HLS | 2968 | 3042 |
| Прямой MP4 | 76 | 118 |

Итоговые времена не везде лучше первичных: в bandwidth-сценарии они выше.
Двух повторов недостаточно для статистического заявления об отсутствии регрессий.
В частности, ускорение отдельных fault-сценариев с новым backoff не переносится
на обычную сеть. Выбранный default сохраняет прежнюю долю при 1–2 задачах;
полная performance acceptance на реальных источниках остаётся открытой.

При подготовке fixture исправлено отсутствие CODECS в master manifest:
оно неверно описывало video-only дорожку и приводило к некорректному ffmpeg map.
Неуспешные прогоны этой неверной fixture остановлены и в итоговые данные не входят.
Четыре ранних cold/warm строки с одинаковой процедурой подготовки исключены;
отдельная исправленная матрица ниже действительно готовит warm-контекст заранее.

## Preview, подготовка и диск

Сделаны 24 корректных прогона: cold/warm × GIF off/on × priority off/on × 3 повтора.
Warm использует текущий проверенный результат того же Inspector/source, а не TTL.
Медианы итогового времени и first_byte_ms (последнее отсчитывается от постановки
job и не включает предварительный cold-анализ):

| Контекст | GIF | Без общего scheduler: итог / first byte, мс | С общим scheduler: итог / first byte, мс |
| --- | --- | ---: | ---: |
| Cold | off | 2640 / 1004 | 2621 / 982 |
| Cold | on | 2633 / 986 | 2594 / 988 |
| Warm | off | 1703 / 975 | 1883 / 994 |
| Warm | on | 1723 / 1032 | 1655 / 979 |

Первый байт с GIF в этом малом сценарии сравним с baseline. Итоговый разброс,
включая warm без GIF, не позволяет обещать ускорение scheduler. Уже запущенный
GIF не вытесняется; новые фоновые операции ограничены и имеют конечную отсрочку.

System/destination temp: по 3 корректных прогона двух HLS.
Медианы **953 / 910 мс**. Это один локальный диск и маленькие файлы, поэтому
default оставлен `system`; альтернативу можно выбрать через
`VIDDOW_TEMP_LOCATION=destination`. Данных внешнего диска нет.

Четыре ресурсных прогона также корректны:

| Задачи | GIF | Sampled RSS дерева harness, МиБ | Sampled workspace peak, байты | CPU reaped children, с |
| --- | --- | ---: | ---: | ---: |
| 1 | off | 116.9 | 1244599 | 1.123 |
| 1 | on | 138.4 | 1245139 | 1.166 |
| 2 | off | 211.9 | 4815272 | 2.069 |
| 2 | on | 208.0 | 2488886 | 2.177 |

RSS берётся по дереву PID/PPID, включая ffmpeg-потомков, Python harness,
fixture server и `ps` sampling overhead. Шаг около 100 мс; пики между отсчётами
могут теряться. Workspace sample также включает готовые результаты и может
пропустить короткий пик копирования. CPU — rusage reaped children, не доказанное
суммарное CPU каждого живого процесса. Эти цифры не выдаются за постоянное
потребление приложения; мониторинга в production нет.

## Восстановление: что доказано

Локальный HTTP-тест передаёт объект **1 048 576 байт**. Один обрыв сохраняет
65 536 байт; следующий Range передаёт только остаток. Суммарно сервер отправляет
ровно 1 048 576 байт, итог совпадает побайтно.

В тесте между Python-процессами три оборванных GET оставляют **196 608 байт**.
Другой процесс после HEAD-проверки получает **851 968 байт** и публикует правильный
файл. Суммарная передача также 1 048 576 байт. Это проверяет фактическое уменьшение
повторных байтов, а не существование `.part`.

Отдельно проверены смена ETag/контента и auth context, 200 вместо 206,
неправильный Content-Range, порча локального префикса, crash-tail после checkpoint,
weak ETag, отсутствие retry для 403, отмена retry-wait, изоляция одинаковых
параллельных запросов, cleanup активного владельца и symlink root.
Автоматического старта после перезапуска не добавлено; pause не введён.
Удаление inactive частей доступно CLI, native command и локальным HTTP endpoint.

## Проверки

Завершающий адресный набор: **118 тестов: 113 прошли, 5 пропущены по ОС**.
Это не полный suite и не browser smoke. Windows Job-тесты не исполнялись на Windows.

```sh
PYTHONPATH=.:tests VIDDOW_TRACE_FILE=/tmp/viddow-optimization-final-tests.jsonl \
python3 -m unittest test_download_runtime test_download_recovery test_work_scheduler \
  test_jobs test_trace_log test_download test_inspector test_media_tracks \
  test_source_auth test_server test_native_session test_tracks_offline \
  test_platform_support test_windows_port test_windows_job test_history -q
```

Первый завершающий прогон обнаружил две старые проверки, ожидавшие совершенно
пустую папку после отмены. Новый store оставляет только служебный каталог и
`.directory.lock`; проверки уточнены так, чтобы любые parts/state/готовые данные
после отмены по-прежнему давали ошибку. Повторный завершающий прогон успешен.
Ранние 54 адресных теста первого этапа не суммируются с этими 118.

`git diff --check` и py_compile изменённых Python-модулей/harness прошли.
Локальные server/native/benchmark исполнения требовали разрешённого выхода из
sandbox только ради loopback bind и локальных процессов; личные cookies не читались.
